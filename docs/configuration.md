# Configuration

An install has three kinds of settings, kept apart on purpose:

| What | Where | Secret? | Committed? |
|---|---|---|---|
| Settings: people, time zone, adapters, limits | `deploy/compose/rhythm.yaml` | no | never (the example is) |
| Compose-level settings: ports, bind address, image tag, folders | `deploy/compose/.env` | no | never (the example is) |
| Secrets: passwords, tokens, keys | one file each under `deploy/compose/secrets/` | yes | never |

`rhythm init` writes all three (`cli/README.md`), and `rhythm doctor` checks them. To do it by hand, copy
`rhythm.example.yaml` to `rhythm.yaml` and `.env.example` to `.env`, edit them, and create the secret files listed
below; `rhythm up` then gives each file the owner and mode its reader needs. `rhythm upgrade` changes none of them but
the image tag in `.env` ([../cli/README.md](../cli/README.md#upgrade)).

After you edit `rhythm.yaml`, `rhythm up` restarts the engine and app on the new settings: the wrappers hand Compose
the file's checksum, since Compose does not notice a changed config file on its own. With plain `docker compose`,
add `--force-recreate`.

The schema for `rhythm.yaml` is `contracts/rhythm.schema.json`. Editors that understand YAML
language-server comments can validate with
`# yaml-language-server: $schema=../../contracts/rhythm.schema.json` at the top of the file.

The engine refuses a key that schema does not name: it will not start, and `rhythm up`, `rhythm doctor` and
`check-config` say which key, on which line, and the known key it most likely meant
(`engine.writelimit (line 12; did you mean engine.writeLimit?)`). Keys are case-sensitive. A misspelt key used to be
left out without a word, so the setting it meant stayed at its default. An adapter this build does not describe (a
plugin's own section under `adapters`) keeps whatever keys it brings.

### Adapters

Each adapter has one section under `adapters`. Every adapter but `embeddings` is off while its section is absent or says
`enabled: false`; `embeddings` is on while its section is absent (the local model loads, as it has since the first
release) and off only with a section that does not say `enabled: true`. The example settings turn on the four that need
no account: `notes`, `csv`, `documents` and `embeddings`. What `rhythm init` writes turns on `csv`, `documents` and
`embeddings`, and `notes` only when it is given `--notes <folder>`. A `rhythm.yaml` without the sections of `notes`,
`csv` and `documents` has them off.

| Adapter | Default | Keys |
|---|---|---|
| `notes` | off; on in the example; `rhythm init` turns it on only when given `--notes <folder>` | `path` (in the engine container, default `/data/notes`), `owner` (default `household`); see [adapters/notes.md](adapters/notes.md) |
| `csv` | off; on in the example and in what `rhythm init` writes | `path` (default `/data/import`), `owner` (default `household`); see [adapters/csv.md](adapters/csv.md) |

| `embeddings` | on, so MiniLM loads, while the section is absent; off with a section that does not say `enabled: true`; on in the example and in what `rhythm init` writes | `model` (`minilm`), `shadow` (none), `backfill` (`false`), `sources` (none; the example lists `documents`, `notes`, `memories`), `thresholds` (`today`); needs the model's files to verify ([below](#embedding-models)) |

`password`, `secret` or `apiKey`. A key ending in `File` holds a path.

### Embedding models

The `embeddings` adapter runs a small local model inside the engine for `semantic_search`, saved documents' passages
and the map's "similar" links. The engine knows three, each pinned to one commit of its public repository and checked
against its SHA-256 before it loads; every vector is stored with its model's id, and vectors of two models are never
compared. `bge-base` was measured against MiniLM ([dev/second-brain-parity/benchmarks.md](dev/second-brain-parity/benchmarks.md#bge-base))
and is refused as `model` and as `shadow`: its vectors are 768-dimensional and the passage table holds 384. `bge-small` can
also be the map's own model (`graph.similarity.model`, [above](#rhythmyaml)): loaded the same way, it makes only the
map's similar and copy links.

| Name | Model | Vectors | Folder variable |
|---|---|---|---|
| `minilm` | all-MiniLM-L6-v2, quantized, mean pooling | 384 | `RHYTHM_MODEL_DIR` |
| `bge-small` | bge-small-en-v1.5, quantized, [CLS] pooling | 384 | `RHYTHM_MODEL_DIR_BGE_SMALL` |
| `bge-base` | bge-base-en-v1.5, fp32, [CLS] pooling (measured only) | 768 | `RHYTHM_MODEL_DIR_BGE_BASE` |

| Key | Default | Meaning |
|---|---|---|
| `adapters.embeddings.model` | `minilm` | the model search, saved documents and the map use. Only `minilm` is accepted for now: another model serves search only after it has been measured against MiniLM on the test set and passed; until then, build its index with `shadow`. `bge-small` was measured in November 2026 and did not pass ([benchmarks](dev/second-brain-parity/benchmarks.md)) |
| `adapters.embeddings.shadow` | none | a second model whose passages the engine builds beside the live model's, a few documents a minute. No search reads them: they are there to be measured, and so that a later change of `model` finds them in place. The live model's passages stay as they are |
| `adapters.embeddings.backfill` | `false` | gives the live model's passages to saved documents that asked for them while the model was off or still loading, a few a minute. Only documents saved while it is on wait for it: with it off, such a document is stored as not indexed, as before |
| `adapters.embeddings.sources` | none (the example settings, and so `rhythm init`, list `[documents, notes, memories]`) | the texts `semantic_search` finds besides saved copies, given the live model's passages a few a minute: `documents` (files added in the app or dropped in the documents folder, and their pages), `notes` (the notes folder), `drive` (Drive documents whose text reads as words), `memories` (native memories not held for review; links on save compare a saved memory with these passages, so without `memories` listed no memory is linked on save). `drive` keeps a copy of each file's text in passages, read again from Drive for every new version, which nothing else does; it is never listed by default. A note's or Drive file's passages answer while the map would show its star (seen by a refresh within `graph.freshnessSeconds`), and a Drive file's only while Drive still holds the version they were read from, checked at each search (eight files at once, at most 5 s a search: a file not confirmed by then is left out, and the answer says how many); past the map's window they are removed. `semantic_search` answers only from the texts listed now: a source taken out stops answering at once, and its passages are removed at the next start. `notes` and `drive` also need their adapter on; `documents` follows the list alone, since uploads stay in the catalog whether or not the documents adapter is on. The tool's description names the texts it serves; with none listed it reads as before. A shadow model indexes the same texts |
| `adapters.embeddings.thresholds` | `today` | the similarity scores the engine reads the model's against. `today`: the map's "similar" links use `graph.similarity`'s numbers, as before. `tuned`: they use the live model's own, re-tuned on the test set's labelled pairs; for MiniLM a similar link from 0.56 instead of 0.6, documents (0.8) and the mutual rule (0.45) as before, so the map draws a few more of them. Measured on the test set, that changes two answers and gains nothing the retrieval check counts, so it does not pass and stays off ([benchmarks](dev/second-brain-parity/benchmarks.md#the-tuned-thresholds-on-the-map)). A `graph.similarity` number set to `null` stays off (`documentThreshold`: the main threshold). Links on save (with `memory.tools: on`, [below](#memory)) read the same switch: `today` links a saved memory to another from 0.78, Second Brain's own number, so no link is drawn more loosely than that; `tuned` from MiniLM's 0.58, the lowest score above every unrelated pair of memories of one scope in the labelled pairs. With `memory.tools: on` it also sets when a save is flagged as a possible copy of a memory of its scope: `today` from a score of 0.85 (Second Brain's starting point, as close as before: nothing was flagged before), `tuned` from the live model's own (MiniLM 0.63), which on the test set's labelled pairs finds all 26 copies and near copies instead of 16, and flags 21 pairs that are not copies instead of 2, contradictions among them, which a person should see anyway ([benchmarks](dev/second-brain-parity/benchmarks.md#the-numbers)); either way a copy is saved and flagged, never refused. The same switch holds the threshold the nightly insight candidate pass (with `memory.tools: on`) reads for two memories alike: `today`, 0.80, the starting point Second Brain set for its own model, no looser than before; `tuned`, the live model's own (MiniLM's 0.52). On the test set's labelled pairs likeness alone finds none of the 8 insight pairs at 0.80 and 1 at 0.52, which is why the pass also pairs two important memories ([benchmarks](dev/second-brain-parity/benchmarks.md#insight-candidates-sb-p5-05)). With `memory.tools: on` it also sets when a standing instruction fires for a question: `today` from a score of 0.67 (Second Brain's starting point, no looser than any value the labelled cases give MiniLM: nothing fired before), which under MiniLM reaches 6 of the test set's 90 questions that should fire and no question that should not; `tuned` from the live model's own (MiniLM's 0.59, the lowest score above every question that should not fire), which reaches 15 of the 90 ([benchmarks](dev/second-brain-parity/benchmarks.md#standing-instructions-sb-p5-12)). Any other value stops the engine at start naming it The contradiction check (with `memory.tools: on`, [below](#memory)) reads the same switch: `today` names a close memory as a possible contradiction from 0.85, the duplicate flag's number, since that flag is all that named a contradiction before, so nothing is named more loosely than that; on the test set's labelled pairs that finds 2 of 21 contradictions (precision 1.000). `tuned` names it from MiniLM's 0.58, finding 16 of 21 with 3 others (precision 0.842, recall 0.762) ([benchmarks](dev/second-brain-parity/benchmarks.md#the-numbers)). It is never above the duplicate flag's number. |

Each model's files come from the folder its variable names (`model_quantized.onnx`, for bge-base `model.onnx`, and `vocab.txt`), or else from
`<data>/models/<name>` in the engine's data volume, downloaded once from the pinned commit when missing. Wrong or
missing files leave that model off; nothing else changes. An engine without internet access needs the files placed
first: for the map model, `model_quantized.onnx` and `vocab.txt` of bge-small in `<data>/models/bge-small` (no variable
needed) or in the folder `RHYTHM_MODEL_DIR_BGE_SMALL` names; until then the map keeps MiniLM's links. The index job keeps a cursor per model, so it resumes where
it stopped after a restart and redoes nothing already done; a document that cannot be indexed is passed over and tried
again on the next round, and a round in which nothing succeeds pauses that model's job for an hour. A note or Drive file
with no readable text is passed over until it changes. The engine log says what each round did, in counts only.

### Memory

Rhythm is gaining memories of its own, which can be private to one person ([dev/memory.md](dev/memory.md)). Every
install runs with `memory.scopes: off`, the household-shares-everything model of [security.md](security.md), until its
operator sets `on`; off, nothing in this section changes what anyone sees.

- `memory.scopes` is `off` unless `rhythm.yaml` says `on`, so an install whose settings predate the key stays off when
  it upgrades. `rhythm init` and the example write `off`.
- `on` is accepted since the scopes mode passed phase 1's exit: every read path filters by scope and the authorisation
  tests pass with it on. Before switching, read [security.md](security.md#per-person-memory-scopes) and run
  `rhythm doctor`, whose preview says what each token would stop reading.
- The engine records the mode in its database. Once a database records `on`, starting with `off` (or with a
  `rhythm.yaml` that has lost the key) stops at start rather than show everyone what scopes kept private; so does a
  database that records no mode.
- The first start with `on` records it and adds everyone then in `people` to Family; a
  person added later joins Family only when the operator adds them ([dev/memory.md](dev/memory.md) section 6.3).

Defaults that are rules rather than settings, for when memories are written:

| What | Default |
|---|---|
| a new memory, with scopes on | private to the person who saved it, unless the call names Family; a client whose token speaks for no one saves only into Family, and only when it says so |
| a new memory, with scopes off | a household memory, visible to everyone; asking for a private one is refused |
| what an AI client saves | a draft, or held for review when it looks like pasted instructions or holds hidden characters, when it comes past the client's 40th write in ten minutes, or when it names a project a held memory made; never canonical on its own. On a person's own channel (the terminal's `rhythm remember`, or a viewer session) words that look like instructions are the person's own and hold nothing; hidden characters still do. A draft becomes canonical only when it is confirmed, which anyone allowed to change the memory may do, an AI client included (but not on a capture, below, which only a person confirms); a hold is released only by a person, in the app's Memories view or with `rhythm release` at the terminal (both with `memory.tools: on`, below), so without it a held memory stays held |
| links on save (with `memory.tools: on`, the embeddings model on and `adapters.embeddings.sources` listing `memories`) | a memory saved or changed through the memory tools or the app's Memories view (a new one, an append, a change or an undo of its words or kind, a release of its hold) is linked to at most 3 memories of its own scope that are closest in meaning, from 0.78 (`adapters.embeddings.thresholds`, above), `relates_to`, or `follows` from it to the one episodic memory written within half an hour before it; never to another scope, a held, forgotten or replaced memory, a pair someone unlinked or dismissed, or a pair flagged as a copy for certain (from 0.95) or named a contradiction, until a person keeps both. Each is automatic, "suggested automatically" until a person makes the same link, and removed by unlinking it, which the author of either memory may do and which keeps it out for good; a memory moving between private and Family loses those that would join two scopes. An edit draws again every one that is still close, however many other memories' saves drew, so the pruning pass takes only those no longer close. The terminal, which loads no model, and `rhythm import` draw none; with any of the three off, a save writes exactly what it wrote before |
| a contradiction (with `memory.tools: on`) | no AI client writes a settling or undoes one: a close memory is named to it and the pair queued for a person, from 0.85 unless `adapters.embeddings.thresholds` is `tuned`; a person keeps both or says which replaces which. An AI client can still withdraw an offer nobody has named, by ending the later memory or editing the words away, and then end the earlier, each step in the audit trail (Q-161) |
| capture lanes (hooks, mail, calendars) | a coding agent's session hook is a file its person installs and turns on ([harness/hooks/](../harness/hooks/README.md)), which saves only through `POST /capture`, with no setting here beyond `memory.capture`; a calendar is the `calendar` adapter, off until its person enters a link; mail is not built (D-159) |
| what a capture token saves (with `memory.capture: on` and `memory.tools: on`) | a draft in the token's one scope (bound to a person, theirs once scopes are on; else Family), never canonical until a person confirms it (an AI client asking to is refused), or held for review on the same rules as an AI client's write; the tag `task` is left off it. A mirror of an outside item is read-only while its connection stands; `rhythm capture disconnect` moves it to the trash |
| what an AI client may do with memories (with `memory.tools: on`) | save, append to, edit, confirm or mark wrong, forget into the trash and undo the memories its token may change, read those its token may read, and see their history and projects; list the ones it may change that may be out of date and, on the person's word, mark one still true without changing it. Never release a hold, delete for good or put a memory into a capsule slot, whatever the client's call says: those are a person's steps. The same setting gives the app its Memories view (`app_memories`), where a person saves, reads, edits, confirms, forgets, restores and undoes memories, reviews the held ones and releases one or several, puts a memory into a capsule slot or takes it out, deletes one from the trash for good, marks a task done or received, snoozes or clears a date, records how a decision turned out, links two memories or unlinks them, says one is still true and takes a memory's flags for a check off; at the terminal a person does the same for themselves (`rhythm release`, `rhythm capsule`, `rhythm delete-forever`, `rhythm forget`, `rhythm set-status`, `rhythm link`, `rhythm unlink`, `rhythm still-true`, `rhythm clear-flags`, `rhythm undismiss`, and `rhythm capsule` with no memory to see a capsule as AI clients are served it). An AI client may still edit the words of a memory a person has slotted, screened for holds like any change |
| a Second Brain import (with `memory.secondBrainImport: on`, at the terminal only) | each memory lands in the importing person's private scope, or in Family when the owner's reviewed scope map names it (the export says neither which workspace a memory was in nor who wrote it), always with the importing person as its author; with `memory.scopes: off` only what the map names for Family comes in. Each gets a new id, with its Second Brain id kept in the origin map, so nothing is matched by title. A memory held for review in Second Brain stays held, and one it served is held here when its words read like instructions to an AI client. Its history starts at the import |

`rhythm doctor` adds, whenever the database can be reached (the engine may be down: a mode mismatch is what stops it
starting): the recorded mode against `rhythm.yaml`'s, tokens bound to a person who is suspended or no longer in
`people`, each source share, and with scopes off a preview of switching on: what each token would stop reading, as

## .env

Names and meanings are in `deploy/compose/.env.example`. The important ones:

- `RHYTHM_CONFIG_FILE`: which settings file the containers read. Until `rhythm.yaml` exists the
  example is used, which runs the app in demo mode.
- `RHYTHM_BIND`: the address published ports listen on. `127.0.0.1` (default) means this computer
  only. `0.0.0.0` means your home network too. Tailscale, Cloudflare and OpenAI tunnel recipes keep the
  default.
- `RHYTHM_APP_PORT` (8080) and `RHYTHM_MCP_PORT` (8181). If you change them, change `app.publicUrl` and
  `engine.publicMcpUrl` too (`rhythm doctor` checks local ones).
- `RHYTHM_NOTES_DIR`, `RHYTHM_IMPORT_DIR`, `RHYTHM_BACKUP_DIR`, `RHYTHM_BACKUP_STAGING_DIR`: host folders, by
  default under `./data` (`rhythm init` asks for the data folder). Notes and imports (CSV files, and documents in
  the import folder's `documents/` folder) are mounted read-only into the engine at `/data/notes` and
  `/data/import`. The fictional samples are `../../demo/notes` and `../../demo/import`. The database and the
  engine's archive live in Docker volumes and go into backups (open question Q-051).
- `COMPOSE_PROFILES`: the adapter containers to start, for example `titles` or `cloudflare` (`rhythm connect` adds
  them).
- `COMPOSE_PROJECT_NAME`: the Compose project (default `rhythm`), which names the stack's containers, networks
  (`<project>_internal`, `<project>_egress`) and volumes; `rhythm init` records it (`--project-name`), and a second
  install on the same computer needs its own (`cli/README.md`).
- `RHYTHM_VERSION`: the image tag; `rhythm init` records the one it runs (`dev` by default), `rhythm upgrade` sets it.
- `RHYTHM_DB_NAME` and `RHYTHM_DB_ADMIN_USER`: the database and its owner (`rhythm`, `rhythm_admin`). Only an install
  whose database already has other names sets them, such as one moved from an older engine
  ([dev/migration-compat.md](dev/migration-compat.md)); Postgres, migrate, backup and restore all use them.
- Exposure recipes add their own (`RHYTHM_TAILSCALE_HOSTNAME`, `RHYTHM_SITE`, `RHYTHM_PROXY_*`, image
  overrides); TrueNAS adds `RHYTHM_PGDATA_DIR` and `RHYTHM_ENGINE_DATA_DIR`. All are in `.env.example`.

There is no login inside Rhythm of Life. Who can open it is decided by where it listens and by the
exposure you choose: this computer, your home network, Tailscale, or Cloudflare Access in front
([security.md](security.md), [deploy/exposure/](../deploy/exposure/README.md)).

## The app's server

The `app` container reads `rhythm.yaml` (mounted at `/etc/rhythm/rhythm.yaml`) for `instance.name`,
`timezone`, `people`, `engine.url` and `app.credentialExpiry`. It serves the browser the name, each person's id and
name and the time zone at `GET /api/instance`, with its mode (`demo` or `live`) and the provider id of the engine's own
stars (`contracts/README.md` 1.3); never the engine's address. It answers only to the install's own names
(`app.allowedHosts` above): opening it as `http://<a name>:8080` on your home network needs that name in
`app.publicUrl` or `app.allowedHosts`, while an IP address always works. It re-reads the file when it changes. An invalid file stops it at start with the
names of the wrong keys; a file that turns invalid while it runs keeps the last good settings.

- **Demo mode** whenever no engine is configured: `engine.url` is empty, or `secrets/app_token` is
  missing, empty or unreadable. The app then shows fictional data labelled DEMO and calls nothing.
- **Live mode** otherwise. Nothing falls back to the app's demo data: a failed read shows as
  unavailable, and an adapter that is off keeps its tiles off the home screen and says Not connected,
  with how to connect it, in Sources & settings. The engine's own fictional seed (`demo.enabled`) is
  shown labelled DEMO.
- **Viewer sessions** only with `app.viewers: on`, which this version refuses: then `/api/viewer` opens one with an
  operator's code and the session's requests reach the engine with its own credential
  ([security.md](security.md#viewer-sessions)). Off, every request is the household view's, as before. A hosted front
  end never has them.
- Health check: `GET /api/health` (it calls nothing upstream).
- Its environment variables (`RHYTHM_CONFIG`, `RHYTHM_ENGINE_URL`, `RHYTHM_APP_TOKEN_FILE`, `HOST`,
  `PORT`, `RHYTHM_CATALOG_PROVIDER` for an install that kept an older engine's star ids, and the
  hosted-platform ones) are listed in `app/server/README.md`.

## Secrets

Rules:

- A secret is a file under `deploy/compose/secrets/` (an adapter's under `secrets/adapters/`), one
  value per file, that only you can open: on Docker Desktop for Windows or Mac, keep the folder inside
  your user profile; on Linux, where each container reads its files as its own user, `rhythm init`,
  `rhythm connect` and `rhythm up` give each file its reader's owner ([below](#owners-and-modes),
  [security.md](security.md#secret-files)).
- Containers get it through Docker secrets at `/run/secrets/<name>` and a `*_FILE` variable naming
  that path. No secret is ever a plain environment variable, a `VITE_*` variable, a command
  argument, a log line or a value in `rhythm.yaml` or `.env`.
- `rhythm init` creates them before the first `up`. If one is missing at `up`, Docker creates an empty
  folder in its place; the services treat that as "not configured", and `rhythm init` replaces the
  folder with the file.
- `rhythm doctor` checks file modes and owners and that no secret-shaped value appears in config.

### Owners and modes

Compose bind-mounts each secret file into the containers, and a bind mount keeps the file's Unix owner
and mode (on Linux, and on Docker Desktop too). Each service runs as its own user: the engine image
(engine, migrate, cli commands that read the database) as uid 1654, the app as uid 1000, the backup
image as uid 70; Postgres reads its password as root before dropping privileges. So `rhythm init`,
`rhythm connect` and `rhythm up` (which runs the cli service as root) give every file this owner and
mode, and no file gives "other" users any access (open question Q-050):

| File | Owner (uid:gid) | Mode | Readers |
|---|---|---|---|
| `postgres_password` | 1654:70 | 0640 | migrate, backup (Postgres as root) |
| `engine_db` | 1654:1654 | 0600 | migrate, engine, cli |
| `app_token` | 1654:1000 | 0640 | engine, app |
| `backup_password` | 70:70 | 0600 | backup |
| `adapters/` and `adapters/<adapter>_<purpose>` | 1654:1654 | 0700, 0600 | engine and its adapter workers |
| `adapters/cloudflare_tunnel_token` | 65532:65532 | 0600 | `cloudflared` (the Cloudflare recipe) |
| `adapters/openai-tunnel_key`, `harness_openai-tunnel_token` | 65532:65532 | 0600 | `openai-tunnel` (the OpenAI tunnel recipe) |
| `harness_<name>_token` | you (the owner of `deploy/compose`) | 0600 | you, to give it to your client |
| `plugin_<name>_token` | 1000:1000 | 0600 | the plugin's container (contracts/README.md 4.1) |
| `capture_<name>_token` | you (the owner of `deploy/compose`) | 0600 | you, to give it to the webhook, CI job or shortcut (`rhythm capture connect <name>`; `--person <id>`: it writes into that person's scope once scopes are on; with `memory.capture` on) |
| `secrets/` itself | you | 0700 | |
| `rhythm.yaml`, `.env` | you | 0644 | every container reads `rhythm.yaml` |

The data folders follow the same idea: `notes` and `import` belong to you (the engine only reads
them), `backups` and `backup-staging` to uid 70. `rhythm up` sets that on an empty folder only, never
on one that already holds files.

| File | Used by | Variable | Created by |
|---|---|---|---|
| `postgres_password` | postgres | `POSTGRES_PASSWORD_FILE` | `rhythm init` |
| `engine_db` | engine, workers | `RHYTHM_DB_FILE` | `rhythm init` (a connection string) |
| `app_token` | app, engine | `RHYTHM_APP_TOKEN_FILE` | `rhythm init`; the database keeps only its hash |
| `harness_<name>_token` | your MCP client | none (you paste it into the client) | `rhythm token create <name>` (`--person <id>`: it speaks for that person) |
| `plugin_<name>_token` | an external plugin | `RHYTHM_INGEST_TOKEN_FILE` | `rhythm token create --role ingest --plugin <name>` |
| `adapters/drive_oauth_client`, `adapters/drive_read_token`, `adapters/drive_edit_token` | drive adapter | `RHYTHM_DRIVE_*_FILE` (optional) | your own Google Cloud project, then `rhythm connect drive` |
| `adapters/garmin_api_key` | garmin adapter (in the engine) | `RHYTHM_GARMIN_API_KEY_FILE` (optional) | your Garmin Connect Personal API Key page; you paste it at a hidden prompt (`rhythm connect garmin`) |
| `adapters/second-brain_token` | second-brain adapter | `RHYTHM_SECOND_BRAIN_TOKEN_FILE` (optional) | you paste it (`rhythm connect second-brain`) |
| `adapters/nightscout_token` | nightscout adapter (optional) | `RHYTHM_NIGHTSCOUT_TOKEN_FILE` | you paste a `readable` access token (`rhythm connect nightscout`) |
| `adapters/calendar_link`, `adapters/calendar_link_2`, `adapters/calendar_link_3` | calendar adapter (the second and third optional) | `RHYTHM_CALENDAR_LINK_FILE`, `RHYTHM_CALENDAR_LINK_2_FILE`, `RHYTHM_CALENDAR_LINK_3_FILE` (optional) | you paste your calendar's private ICS link at a hidden prompt (`rhythm connect calendar`); it is never shown back |
| `adapters/cloudflare_tunnel_token` | cloudflare recipe (`cloudflared`) | `TUNNEL_TOKEN_FILE` | the Cloudflare dashboard |
| `proxy_users` | the Caddy example (`deploy/exposure/reverse-proxy/`) | none (imported by the Caddyfile) | `caddy hash-password`, one line per person |
| `adapters/openai-tunnel_key` | openai-tunnel recipe (the tunnel client) | none: mounted at `/run/secrets/openai-tunnel_key`, read as `file:` | a restricted runtime key from the OpenAI platform, pasted at `rhythm connect openai-tunnel` |
| `harness_openai-tunnel_token` | openai-tunnel recipe (sent to the engine as its bearer) | none: mounted at `/run/secrets/openai-tunnel_token` | `rhythm token create openai-tunnel` |
| `backup_password` | backups | `RESTIC_PASSWORD_FILE` | `rhythm init`; store a copy offline |

`engine_db` is the engine's own login, for example
`Host=postgres;Database=rhythm;Username=rhythm_engine;Password=<random>`. The migrate service creates that
login (or updates its password) with data rights only, using `postgres_password`. See `docs/dev/engine.md`.
